# Google-вход и сохранение в аккаунте Supabase

Код интеграции подготовлен. Без реального проекта Supabase и включённого Google-провайдера вход не работает: приложение честно показывает это в настройках и продолжает сохранять данные на устройстве.

Можно установить и подключить плагин Supabase в чате для настройки базы. Данные Google OAuth вводятся в панели Supabase; Google Client Secret не нужно передавать в чат или добавлять во frontend.

## 1. Создайте проект Supabase

Откройте [Supabase Dashboard](https://supabase.com/dashboard), создайте организацию и проект. Сохраните пароль базы в своём менеджере паролей. Для приложения понадобятся **Project URL** и **Publishable key** (`sb_publishable_…`), доступные в настройках проекта. Поддерживается также старый публичный `anon` key.

`service_role`, `sb_secret_…`, пароль PostgreSQL и Google Client Secret не предназначены для браузера. В этом приложении они не используются. Различия ключей описаны в [документации Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

## 2. Подготовьте таблицу и правила доступа

В SQL Editor проекта выполните содержимое:

```
supabase/migrations/202610300001_reading_accounts.sql
```

Миграция создаёт `public.reading_libraries`, политику чтения собственной строки и функцию `save_reading_library`. Её можно повторно выполнить: существующие библиотеки сохраняются.

RLS включён. Анонимный пользователь не имеет доступа к библиотекам. Пользователь читает только собственную строку. Запись выполняется только через функцию, которая проверяет `auth.uid()`, переданный идентификатор и ожидаемую версию данных. Прямые INSERT/UPDATE/DELETE для клиентских ролей запрещены. Политики основаны на [Row Level Security Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 3. Настройте Google OAuth

В [Google Auth Platform](https://console.cloud.google.com/auth/overview) выберите или создайте проект. Заполните Branding / Audience / контактные данные и создайте OAuth client типа **Web application**.

В **Authorized redirect URIs** добавьте адрес callback из настроек Google-провайдера вашего проекта Supabase, обычно:

```
https://YOUR_PROJECT_REF.supabase.co/auth/v1/callback
```

В Supabase откройте Authentication → Sign In / Providers → Google, включите провайдер и вставьте Google Client ID и Client Secret. Если OAuth-приложение Google находится в тестовом режиме, добавьте адреса пользователей в список тестировщиков. Для доступа остальных пользователей потребуется соответствующая публикация OAuth-приложения в Google.

Приложение использует перенаправление OAuth с PKCE и запрашивает только `openid email profile`. Доступ к Google Drive, почте и календарю не запрашивается. Точная последовательность настройки — в [официальном руководстве Google-входа через Supabase](https://supabase.com/docs/guides/auth/social-sign-in/auth-google).

## 4. Разрешите возврат в приложение

В Supabase Authentication → URL Configuration укажите production-адрес в **Site URL**. В **Redirect URLs** добавьте точные адреса, которые будете использовать:

```
http://127.0.0.1:5173/
http://localhost:5173/
http://127.0.0.1:4173/
https://YOUR_APP_DOMAIN/
```

Замените production-адрес реальным доменом. Приложение возвращается на `window.location.origin + '/'`. Callback Google в Supabase и конечный адрес приложения — это разные настройки. См. [Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).

## 5. Подключите проект к приложению

Создайте `.env.local` в корне проекта по образцу `.env.example`:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_PUBLIC_KEY
```

Укажите реальные публичные значения. Локальные `.env`-файлы исключены из Git. Все переменные с префиксом `VITE_` попадают в клиентскую сборку, поэтому секретов в них быть не должно.

Перезапустите dev-сервер:

```sh
npm run dev
```

Для HTTPS-хостинга добавьте те же две переменные в окружение сборки и выполните:

```sh
npm ci
npm run build
```

После изменения значений нужна новая сборка. Готовые статические файлы находятся в `dist/`.

## 6. Проверьте реальный вход

1. Откройте настройки приложения и нажмите «Войти через Google».
2. После возврата проверьте адрес аккаунта и сообщение «Всё сохранено в аккаунте».
3. Если раньше пользовались без входа, нажмите «Перенести данные с этого устройства» и подтвердите перенос. Существующие облачные книги сохраняются; расходящиеся версии одной книги не объединяются молча.
4. Добавьте книгу, запишите чтение, измените годовую цель и дождитесь успешной синхронизации.
5. Откройте приложение в другом профиле браузера или на другом устройстве. Войдите в тот же аккаунт и проверьте библиотеку.
6. Проверьте отсутствие сети, её восстановление и конфликт одновременного редактирования. Несинхронизированные изменения должны оставаться на устройстве.
7. Отдельно проверьте вход и возврат в установленную PWA на физических Android/iOS-устройствах: их поведение при OAuth зависит от браузера и режима установки.

Реальный диалог Google и инфраструктура вашего Supabase-проекта не проверялись без подключения аккаунта и настройки провайдера.

## Поведение синхронизации

- Каждая учётная запись имеет отдельный локальный кеш и отдельную облачную строку. Выход возвращает в локальную библиотеку без аккаунта; приватная библиотека аккаунта не копируется в гостевой режим.
- Книги, обложки, начальный прогресс, записи чтения, планы, долги (вычисляемые из планов и записей), выходные и настройки сохраняются вместе. Год завершения вычисляется из сохранённой даты окончания.
- Изменения сначала записываются в IndexedDB, затем отправляются в Supabase. При работающем сохранённом сеансе можно редактировать кешированную библиотеку без сети; отправка возобновляется при подключении. Первый вход и повторная авторизация после истечения сеанса требуют интернета.
- Синхронизация запускается после изменения, при возврате к приложению, после восстановления сети и каждые 20 секунд в открытом приложении. Можно запустить её вручную в настройках.
- Закрытая PWA не выполняет гарантированную фоновую отправку: дождитесь сообщения об успешном сохранении перед сменой устройства.
- Если оба устройства изменили библиотеку, автоматическая запись останавливается. Пользователь скачивает нужные копии и явно выбирает версию. Запрос с устаревшей версией сервер отклоняет; новые изменения на другом устройстве не затираются без подтверждения.
- При переносе локальной библиотеки добавляются книги с отсутствующими идентификаторами. Одинаковые версии не дублируются. Различающиеся версии одной книги требуют ручного решения через резервные копии. Существующие годовые цели аккаунта имеют приоритет; отсутствующие годы добавляются из локальных данных.
- На текущем этапе библиотека хранится цельным JSON-снимком, включая обложки, с лимитом 50 МиБ на снимок. Обложки до 3 МиБ каждая. Для очень больших библиотек потребуется раздельное хранение книг и изображений. Ошибка загрузки не удаляет локальные данные.

## Проверки

```sh
npm run typecheck
npm test
npm run build
npx playwright test
npx playwright test --config playwright.account.config.ts
```

`npm test` проверяет алгоритмы чтения, изоляцию кешей, отправку отложенных изменений, конфликты и работу SQL-миграции в PostgreSQL через PGlite. В том числе проверены запрет чтения чужих строк, запрет прямой записи и атомарность проверки версии.

Отдельный account-набор браузерных тестов запускает Vite на порту 4175 с заведомо тестовым публичным ключом и перехватывает ответы Supabase. Он проверяет интерфейс аккаунта, выход, конфликты, OAuth-адрес и наличие PKCE challenge. Эти тесты не заменяют проверку реального Google-входа, DNS, разрешённых URL и настроек облачного проекта.
